# 0004. Доступ вендора: власні задачі під RLS, заголовок запуску — функцією, обмеження в базі до появи вендорів

- Статус: прийнято
- Дата: 2026-11-06
- AC: AC-VENDOR-01, AC-VENDOR-02, AC-VENDOR-03, AC-VENDOR-04, AC-VENDOR-05, AC-VENDOR-06, AC-VENDOR-07, AC-VENDOR-08, AC-VENDOR-09, AC-VENDOR-10

## Контекст

Вимога PM (solomchaak/property-workflows-spec#39) додає роль `vendor`: менеджер призначає вендора виконавцем частини задач під час запуску, а вендор бачить і позначає виконаними лише свої задачі. Матриця прав забороняє вендору шаблони, форму запуску, чужі задачі, email інших людей і службові дані запуску. Правила мають діяти й для прямих запитів у Data API (публічний ключ лежить у бандлі), а не лише на сторінках. До цього зрізу будь-який автентифікований користувач із роллю не `null` читав шаблони, `can_see_run` пускав виконавця задачі до всього запуску, а `list_assignable_users` віддавала email кожному. Нова роль у цих відкритих місцях розкрила б чуже. PM на питання solomchaak/property-workflows-spec#41–#50 ще не відповів, тому частина рішень нижче — робочі припущення за рекомендованим варіантом питання. План — `openspec/changes/impl-vendor-access/design.md`; ADR 0001 і 0002 діють без змін.

## Рішення

- **Роль без нових таблиць.** `profiles_role_check` розширено значенням `vendor`; `default` лишається `'manager'`, роль вендора виставляє лише `service_role` (скрипт `npm run users:demo`). Колонковий `grant update (full_name)` не дає вендору змінити собі роль.
- **Рядки задач — під RLS, звуженою до власних.** Політика `select` для `run_tasks`: `private.can_see_run(run_id)` або (роль `vendor` і `assignee_id = (select auth.uid())`); для `run_sections` — `can_see_run` або `private.vendor_has_task_in_section(id)`. Пряме читання вендором повертає рівно його задачі й секції з ними (AC-VENDOR-04, AC-VENDOR-06). `private.can_see_run` для ролей, окрім `admin` і `manager`, повертає `false`.
- **Заголовок запуску — вузькою функцією.** `runs` для вендора закрита: там `template_id`, `template_version`, `manager_id`, а колонковий `grant` не розрізняє ролей застосунку. Назву випадку, статус і лічильники «Your tasks: N of K done» повертає `public.list_vendor_runs(p_run_id)` (`security invoker`) → `private.list_vendor_runs` (`security definer`, `set search_path = ''`), лише по задачах викликача-вендора (AC-VENDOR-03, AC-VENDOR-10).
- **Закрито все чуже.** `templates_select_visible` і `private.can_read_template_version` — лише `manager`/`admin` (AC-VENDOR-08); `launch_run` першим рядком вимагає `manager`/`admin`, інакше `Not authorized` (`42501`) до будь-якого запису (AC-VENDOR-09); `list_assignable_users` повертає `id` і `email` лише викликачу-менеджеру/адміну й включає вендорів (AC-VENDOR-01, AC-VENDOR-02).
- **«Немає» і «заборонено» не відрізняються.** `mark_task_done` для вендора без жодної задачі в запуску (або без такої задачі) дає `Run not found` (`P0002`), як і сторінка; вендор, що має інші задачі в цьому запуску, але не виконавець цієї, отримує дослівне повідомлення AC-TASK-03. Задача в обох випадках не змінюється (AC-VENDOR-06, AC-VENDOR-07). Власна задача позначається й у запуску «completed» (AC-VENDOR-05).
- **Порядок: спершу обмеження, потім вендори.** Три міграції (`vendor_role`, `vendor_reads`, `vendor_mark_done`) звужують політики й функції; користувачів із роллю `vendor` на проді створюємо після злиття груп 1–4. До того «вендор» існує лише в тестах PGlite.
- **Сторінки лише дублюють базу.** Вендор: `/runs` (таблиця або «No tasks assigned to you yet.»), `/runs/[id]` (власні задачі, «Mark as done» з діалогом «This cannot be undone» на кожній), решта маршрутів — «Not enough rights» із посиланням «Back to runs»; вхід без явного `next` веде вендора на `/runs`.
- **Робочі припущення до відповідей PM** (за рекомендованим варіантом): #41 A, #42 A, #43 B, #44 A, #46 A, #47 B, #48 B, #49 A, #50 A. Питання #45 (зміна ролі користувача з активними запусками) не реалізуємо.

## Розглянуті варіанти

- Вендор читає `runs` напряму з політикою `can_see_run` — розкриває версію шаблону й менеджера запуску, які матриця прав вендору забороняє.
- Вендор читає все лише функціями, а таблиці для нього порожні — пряме читання `run_tasks` мало б повертати рівно його задачі (#50, варіант A), а не «нічого».
- Роль у JWT (Custom Access Token Hook) — токен застаріває до оновлення, потрібен хук і його емуляція в тестах; роль лишається в `profiles.role` (ADR 0002).
- Перевірка ролі лише в Server Actions і на сторінках — правило жило б у коді, а прямий запит із токеном вендора його обминав би.
- Відмова зі своїм текстом для запуску без задач вендора — розкрила б, що запуск існує, тож перебір ідентифікаторів щось повідомляв би.

## Наслідки

- Простіше: правило прав однакове для сторінки, дії й прямого запиту; поведінка перевіряється тестами бази на PGlite без Docker (`tests/db/vendor-access.test.ts`).
- Складніше: дві схеми читання (таблиці під RLS і `list_vendor_runs`) мають лишатися узгодженими — лічильники беруться з тих самих рядків `run_tasks`; кожна нова привілейована дія вендора — функція в `private` з обгорткою в `public`.
- Якщо PM відповість інакше, зміниться лише позначене «рішення до …#N» місце: окрема зміна специфікації `clarify-vendor-access` і нова задача; ID AC не змінюються.
- Ризик заміни політик і `check` описано в PR груп 1–3; деструктивних операцій немає.

## Як перевіряємо

- PGlite (`tests/db/vendor-access.test.ts`, напряму від імені вендора через `asUser`):
  - вендор призначається виконавцем задач 3 і 4, решта — менеджер; список виконавців містить email менеджера, адміністратора й вендорів без імен і ролей (AC-VENDOR-01, AC-VENDOR-02);
  - `launch_run` від вендора — виняток, `count(*)` у `runs` не змінився (AC-VENDOR-09);
  - `run_tasks` — рівно його задачі, `run_sections` — лише секції з ними, `runs`, чужі `profiles` і `templates*` порожні (AC-VENDOR-04, AC-VENDOR-08);
  - `list_vendor_runs` — лише його запуски з лічильниками; запуск без його задач і вендор без задач — порожньо (AC-VENDOR-03, AC-VENDOR-06, AC-VENDOR-10);
  - `mark_task_done` — власна задача стає «done», чужа лишається «to_do» в обох випадках рішення #48 (AC-VENDOR-05, AC-VENDOR-07).
- Тести сторінок і дій (`src/app/runs/vendor-pages.test.tsx`, `src/app/vendor-refusals.test.tsx`, `src/app/runs/[id]/actions.test.ts`, `src/lib/runs/*.test.ts`, `src/lib/auth/refusal-link.test.ts`): тексти AC, відмова без запиту даних шаблонів, лише власна кнопка «Mark as done».
- Мутаційна перевірка (описи PR груп 1–4; SQL-мутанти — `npm run mutation:sql`, `scripts/mutants.mjs`): прибрана перевірка ролі в `launch_run`, розширений `list_assignable_users`, прибрана умова `assignee_id` у політиці `run_tasks`, повернено `is not null` у `templates_select_visible`, прибрана гілка `vendor` у `mark_task_done` → відповідні тести AC червоні.
- UAT на проді (група 6): окрема специфікація на кожен AC; для AC-VENDOR-07 і AC-VENDOR-09 — прямий виклик `rpc` під вендором і екран менеджера, що показує «що не змінилося».
